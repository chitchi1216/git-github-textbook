Pull Request：枝を GitHub で合流させる

この章でできるようになること
  • Pull Request（PR）が何のためにあるかを、説明できる
  • 作業した枝を、GitHub に送れる（git push -u origin 枝の名前）
  • GitHub の画面で、PR を作り、変更を見直して、合流（マージ）できる
  • 合流のあと、手元と GitHub の枝を、片付けられる

7-1. Pull Request とは

第6章では、作業した枝を、自分のパソコンの中で git merge して、main に合流させました。この章では、同じ「合流」を、GitHub の画面で行います。そのための仕組みが、Pull Request（プルリクエスト。略して PR）です。

PR は、ひとことで言うと、「この枝を、main に合流させてください」という提案です。提案には、「何を変えたか」が、画面で一覧になって付いてきます。それを見て、問題がなければ、ボタンで合流させます。

一人なのに、なぜ「提案」するの？
  • 合流の前に、変更を「見直す」場ができる。手元の git merge は、打てば、すぐに合流します。PR では、変更の一覧を、落ち着いて見直してから、合流できます。
  • 「なぜ変えたか」が、記録に残る。PR の説明は、あとから、いつでも読み返せます。
  • ほかの人との作業でも、まったく同じ流れになる。共同開発では、ほかの人に見直し（レビュー）を頼んでから、合流させます。一人のうちに、流れに慣れておくと、第9章で困りません。
言葉意味名前の由来
Pull Request（PR）「この枝を、合流させてください」という提案。GitHub の画面で作るpull ＝ 引っ張る、request ＝ お願い
レビュー（review）変更を見直して、問題がないか確かめることreview ＝ 見直す
base（ベース）合流先の枝。ふつうは mainbase ＝ 土台
compare（コンペア）合流させたい枝。作業した枝compare ＝ 比べる
マージ（merge）合流させること。第6章と同じmerge ＝ 合流させる
第6章（手元で合流）第7章（PR で合流）
合流させる場所自分のパソコンGitHub
合流させる操作git merge 枝の名前画面の「Merge pull request」ボタン
合流の前の見直し自分で git diff などを打つ変更の一覧が、画面に付いてくる
手元の main への反映合流した時点で、反映済みgit pull で受け取る

7-2. 実習A：枝を GitHub に送る

第4章・第6章で使った my-notes で、自己紹介のファイル profile.txt を、別の枝で作り、その枝を GitHub に送ります。

打つ前に確認
  • 入力モードは「半角英数」に。
  • 場所は C:\work\my-notes（OneDrive の外）。git を打つ前に、プロンプトの場所を確かめます。
  • 表示のコミットID（2e1f0d9 など）や、URL の chitchi1216 は、人によって違います。URL は、自分の GitHub のユーザー名に読み替えてください。
  • profile.txt には、本名や住所など、知られたくないことは書かないでください。この章では、趣味などで十分です。

手順1：準備する

cd C:\work\my-notes
git switch main
git status
git pull
PS C:\work> cd C:\work\my-notes
PS C:\work\my-notes> git switch main
Already on 'main'
Your branch is up to date with 'origin/main'.
PS C:\work\my-notes> git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
PS C:\work\my-notes> git pull
Already up to date.

第6章と同じく、main にいて、「きれい」で、最新になっていることを確かめてから、始めます。Already on 'main' は「すでに main にいます」、Already up to date. は「すでに最新です」という意味です。

手順2：枝を作って、作業して、記録する

git switch -c add-profile
New-Item profile.txt
notepad profile.txt

メモ帳が開いたら、Hello! I am learning Git. と書いて、最後に Enter で改行して、保存して閉じます。続けて、記録します。

git add profile.txt
git commit -m "Add profile.txt"
PS C:\work\my-notes> git commit -m "Add profile.txt"
[add-profile 2e1f0d9] Add profile.txt
 1 file changed, 1 insertion(+)
 create mode 100644 profile.txt

ここまでは、第6章とまったく同じです。違うのは、ここからです。第6章では main に戻って git merge しましたが、今回は、枝のまま、GitHub に送ります。

手順3：枝を、GitHub に送る

git push -u origin add-profile
PS C:\work\my-notes> git push -u origin add-profile
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Writing objects: 100% (3/3), 320 bytes | 320.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0
remote:
remote: Create a pull request for 'add-profile' on GitHub by visiting:
remote:      https://github.com/chitchi1216/my-notes/pull/new/add-profile
remote:
To https://github.com/chitchi1216/my-notes.git
 * [new branch]      add-profile -> add-profile
branch 'add-profile' set up to track 'origin/add-profile'.

読んでみましょう。

  • * [new branch] add-profile -> add-profile：GitHub に、新しい枝 add-profile ができた。
  • remote: Create a pull request for 'add-profile' …：GitHub からの「この枝の PR を作るなら、この URL へ」という案内。
  • branch 'add-profile' set up to track 'origin/add-profile'.：手元の add-profile の送り先を、GitHub の add-profile として覚えた。

💡 -u は upstream（上流＝送り先）の頭文字です。第4章で git push -u origin main と打ったのと、同じ意味です。一度覚えさせれば、この枝では、次から git push だけで送れます。

「src refspec add-profile does not match any」と出たら 「add-profile という枝が、手元に見つかりません」という意味です。枝の名前の打ち間違いか、まだ1回も記録（commit）していないことが、よくある原因です。git branch で枝の名前を、git log --oneline で記録を、確かめてから、打ち直します。

7-3. 実習B：PR を作る

ここからは、ブラウザで、GitHub の my-notes のページを開いて、操作します。

手順1：「Compare & pull request」を押す

my-notes のページの上のほうに、黄色い帯で「add-profile had recent pushes」（add-profile に、最近 push がありました）と出ています。その右の、緑の「Compare & pull request」ボタンを押します。

ボタンが見当たらないとき 黄色い帯は、しばらくすると消えます。そのときは、次のどちらかで、同じ画面を開けます。
  • 手順3の git push の出力にあった URL（https://github.com/…/my-notes/pull/new/add-profile）を、ブラウザで開く。
  • ページ上の「Pull requests」タブ → 緑の「New pull request」→ 右側の「compare:」で add-profile を選ぶ → 変更の比較が表示されたら、緑の「Create pull request」を押す。ここで初めて、タイトルと説明の入力欄が出ます（最後に、もう一度、同じ名前のボタンで PR を作ります）。

手順2：向きを確かめて、タイトルと説明を書く

「Open a pull request」（PR を開く）という画面になります。まず、上のほうの向きを確かめます。

base: main  ←  compare: add-profile

「add-profile を、main に合流させる」という向きです。矢印は、合流する方向を表しています。その横に、緑の文字で「Able to merge.」（合流できます）と出ていれば、問題ありません。

次に、入力欄を書きます。

  • タイトル（Add a title）：記録が1つだけなら、そのメッセージ（Add profile.txt）が、自動で入っています。そのままで構いません。
  • 説明（Add a description）：何を、なぜ変えたかを書きます。今回は、次のように書いてみましょう（書き方は、7-6 でくわしく見ます）。
profile.txt を追加しました。自己紹介を書いておくためです。

書けたら、下の緑の「Create pull request」（PR を作る）ボタンを押します。

手順3：できた PR を、眺める

PR ができました。タイトルの横に #1 のような番号が付き、緑の「Open」（開いている＝まだ合流していない）という印が出ています。画面には、いくつかのタブがあります。

タブ見られるもの
Conversation（会話）PR の説明と、コメントのやりとり。合流のボタンも、ここにある
Commits（コミット）この PR に含まれる記録の一覧
Files changed（変更されたファイル）変更の中身。git diff の画面版

※ PR の番号は、リポジトリの中で、1から順に付きます。以前に PR を作ったことがあれば、#2 などになります。

☕ ここで一区切りしてOK 次は「7-4. 実習C」からです。PR は、合流させるまで、開いたまま残っています。再開するときは、PowerShell を開き、cd C:\work\my-notes で戻ってから、ブラウザで my-notes の「Pull requests」タブを開いてください。

7-4. 実習C：自分で見直す

合流させる前に、変更を見直します。共同開発では、ほかの人が行う「レビュー」を、今回は、自分で行います。

手順1：「Files changed」で、変更を見る

PR の「Files changed」タブを開きます。profile.txt の緑の行（+ の付いた行）が、今回、追加された行です。第3章の git diff と同じ読み方です。

見るだけでなく、次の3つを確かめるのが、見直し（レビュー）です。

  • 変えるつもりのファイルだけか。関係のないファイルや、消すつもりのない行が、混ざっていないか。
  • 誤字や、書き漏らしがないか。
  • 公開したくない情報がないか。本名、住所、メールアドレス、パスワードなどが、書かれていないか。

手順2：行に、コメントを付けてみる

行の上にマウスを置くと、行番号の横に、青い「+」が出ます。押すと、その行へのコメントを書けます。ためしに、次のように書いて、「Comment」（画面によっては「Add single comment」）を押してみましょう。「Start a review」（レビューを始める）は、コメントを何個かためて、まとめて送るためのものです。今回は、選ばなくて大丈夫です。

趣味も書いておきたい。

コメントは、「Conversation」タブにも表示されます。共同開発では、こうして「ここは、こう直したほうがいい」と、行を指して、やりとりします。

自分の PR は、自分で「承認」できない レビューには、「承認する（Approve）」という操作もあります。ただし、自分が作った PR は、自分で承認できません（画面で選べなくなっています）。承認は、ほかの人に頼むものだからです。ほかの人に頼むときは、PR の画面の右側の「Reviewers」（レビューする人）に、相手を指定します。第9章で、使います。

手順3：直して、もう一度送る

コメントに書いたとおり、趣味を足します。PowerShell に戻って、add-profile にいることを確かめてから、作業します。

git branch
notepad profile.txt

* add-profile になっていれば、大丈夫です。メモ帳で、2行目に Hobby: walking（趣味：散歩。好きな趣味に変えてOK）と書いて、最後に Enter で改行して、保存して閉じます。記録して、送ります。

git add profile.txt
git commit -m "Add hobby to profile.txt"
git push
PS C:\work\my-notes> git commit -m "Add hobby to profile.txt"
[add-profile 5b4a3c2] Add hobby to profile.txt
 1 file changed, 1 insertion(+)
PS C:\work\my-notes> git push
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Writing objects: 100% (3/3), 330 bytes | 330.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0
To https://github.com/chitchi1216/my-notes.git
   2e1f0d9..5b4a3c2  add-profile -> add-profile

実習A で -u を付けたので、今度は git push だけで、add-profile に送れました。

ブラウザに戻って、PR のページを再読み込み（F5）します。「Commits」タブの記録が 2つに増え、「Files changed」にも、2行目が加わっているはずです。PR は、作ったあとも、同じ枝に push するだけで、自動で更新されます。直してから、作り直す必要はありません。

7-5. 実習D：合流させて、片付ける

手順1：GitHub で、合流させる

PR の「Conversation」タブの下のほうに、緑の「Merge pull request」（PR を合流させる）ボタンがあります。押すと、確認の欄が出るので、「Confirm merge」（合流を確定する）を押します。

印が、紫の「Merged」（合流済み）に変わりました。GitHub の main に、profile.txt が届いています。

ボタンの右の「▼」は、今は触らない 「Merge pull request」の右の ▼ では、合流のさせ方を選べます。この教材では、最初に選ばれている「Create a merge commit」（合流コミットを作る）だけを使います。第6章の実習B と同じ、「合流コミット」ができる方法です。

手順2：GitHub の枝を、片付ける

合流させると、すぐ下に「Delete branch」（枝を削除する）ボタンが出ます。押して、GitHub の add-profile を消します。

第6章の git branch -d と同じく、消えるのは名札だけです。記録は main に合流済みなので、消えません。PR のページも、そのまま残ります。

手順3：手元の main に、受け取る

PowerShell に戻ります。GitHub で合流させただけなので、手元の main は、まだ古いままです。main に移って、受け取ります。

git switch main
git pull
PS C:\work\my-notes> git switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.
PS C:\work\my-notes> git pull
remote: Enumerating objects: 1, done.
remote: Counting objects: 100% (1/1), done.
remote: Total 1 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (1/1), 920 bytes | 61.00 KiB/s, done.
From https://github.com/chitchi1216/my-notes
   f1a29e4..9c8d7e6  main       -> origin/main
Updating f1a29e4..9c8d7e6
Fast-forward

 1 file changed, 2 insertions(+)
 create mode 100644 profile.txt

※ git switch main のあとの up to date（最新です）は、「最後に GitHub を確かめたときの情報では」という意味です。GitHub で合流させたことは、pull するまで、手元の Git には分かりません。

手元の main にも、profile.txt が届きました。履歴の図を見てみましょう。

git log --oneline --graph --all
PS C:\work\my-notes> git log --oneline --graph --all
*   9c8d7e6 (HEAD -> main, origin/main) Merge pull request #1 from chitchi1216/add-profile
|\
| * 5b4a3c2 (origin/add-profile, add-profile) Add hobby to profile.txt
| * 2e1f0d9 Add profile.txt
|/
*   f1a29e4 Merge branch 'feature-a'

いちばん上に、GitHub が作った合流コミット（Merge pull request #1 …）があります。メッセージに、PR の番号が入っているので、あとから「どの PR で合流したか」をたどれます。（下に、第6章までの記録が続きます。）

手順4：手元の枝と、名残を片付ける

git branch -d add-profile
git fetch --prune
git branch -a
PS C:\work\my-notes> git branch -d add-profile
Deleted branch add-profile (was 5b4a3c2).
PS C:\work\my-notes> git fetch --prune
From https://github.com/chitchi1216/my-notes
 - [deleted]         (none)     -> origin/add-profile
PS C:\work\my-notes> git branch -a
* main
  remotes/origin/main
  • git branch -d add-profile：手元の枝を消します（第6章と同じ）。
  • git fetch --prune：手元には、「GitHub に add-profile がある」という古い情報（origin/add-profile）が残っています。GitHub で消えた枝の情報を、手元からも刈り取ります。(none) の行は「origin/add-profile を消した」という意味です。
  • git branch -a：手元の枝に加えて、GitHub の枝の情報（remotes/origin/…）も、まとめて表示します。main だけになっていれば、片付け完了です。

💡 prune は、庭木の「枝を刈り込む」という意味です。-a は all（すべて）の頭文字です。

PR の流れ（まとめ）

  1. git switch -c 枝の名前：枝を作って、移る
  2. 作業して、add → commit
  3. git push -u origin 枝の名前：枝を GitHub に送る
  4. GitHub で、PR を作る（Compare & pull request → Create pull request）
  5. 「Files changed」で見直す。直すなら、手元で commit → git push
  6. Merge pull request → Confirm merge → Delete branch
  7. git switch main → git pull → git branch -d 枝の名前 → git fetch --prune
GitHub の画面だけでも、PR を作れる 第4章のチャレンジ1で、GitHub の画面で hello.txt を編集したとき、「Commit changes」の画面に、Create a new branch for this commit and start a pull request（この記録のために新しい枝を作り、PR を始める）という選択肢がありました。これを選ぶと、GitHub が枝を作り（名前は ユーザー名-patch-1 のように自動で付きます。変えてもOK）、そのまま「Open a pull request」の画面に進みます。そこからあとは、この章の 7-3 の手順2と同じです。
  • 誤字を1文字直すような小さな変更なら、この方法が手軽です。
  • 合流させたあとは、手元で git switch main → git pull → git fetch --prune を打ちます。枝は GitHub にしか作られていないので、git branch -d は要りません。

7-6. 伝わる PR の書き方

PR の説明は、未来の自分や、ほかの人への手紙です。半年後に読み返しても分かるように、次の3つを書く習慣をつけましょう。

項目書くこと
何を何を変えたか。ファイル名や、変えた中身
なぜなぜ変えたか。いちばん大切。変更の中身は画面で見られるが、理由は書かないと残らない
確かめたこと動くか、表示が正しいかなど、自分で確かめたこと

見本です。説明の欄には、この形のまま書けます。

## 何を
profile.txt に、自己紹介と趣味を書きました。

## なぜ
自分のリポジトリを見た人に、どんな人が書いているか分かるようにするためです。

## 確かめたこと
- Files changed で、2行が追加されていることを見ました。

説明の欄では、## で始まる行が見出しに、- で始まる行が箇条書きになります（「Markdown」という書き方です）。入力欄の上の「Preview」タブを押すと、仕上がりを確かめられます。

PR は、小さく分ける 1つの PR には、1つの作業だけを入れます（第6章の「1つの作業を1つの枝に」と同じ考えです）。「プロフィールを書く」と「誤字を直す」は、別々の PR にします。小さい PR ほど、見直しやすく、間違いに気づきやすくなります。
☕ コーヒーブレイク：なぜ「Pull」Request なのか（読み飛ばしてOK）

自分が送る（push）のに、なぜ「pull（引っ張る）」と呼ぶのでしょうか。それは、相手の立場から見た言葉だからです。「私の変更を、あなたのリポジトリに引っ張って（pull して）ください」というお願い（request）、という意味です。

もともと Git には、「私の変更を、取り込んでください」という依頼文を作って、メールで送る仕組みがありました。GitHub は、このやりとりを、ブラウザの画面でできるようにしました。そのため、同じ「Pull Request」の名前が使われています。

なお、GitHub とよく似たサービスの GitLab では、同じ仕組みを「Merge Request（合流のお願い）」と呼びます。こちらは、合流させる側から見た名前です。呼び名は違っても、中身は同じです。

※ 年代や経緯には、諸説あります。

7-7. チャレンジ

必須ではありません。実習A〜D が終わった状態から、始めます。

🎯 チャレンジ1 ★☆☆　合流済みの PR を、探す

合流させた PR は、「Pull requests」タブの一覧から、消えたように見えます。実習で作った PR を、もう一度、開いてください。

ヒント

一覧の上に、「Open」と「Closed」の2つの切り替えがあります。

こたえと解説

「Pull requests」タブで、「Closed」（閉じたもの）を押します。紫の印の付いた PR が、合流済みのものです。一覧に最初に出るのは、まだ開いている（Open）PR だけです。合流させた PR は「閉じた」扱いになりますが、消えたわけではありません。説明やコメントも、いつでも読み返せます。

🎯 チャレンジ2 ★★☆　合流させずに、PR を閉じる

試してみたけれど、やっぱり要らない、という変更もあります。枝 try-close で、hello.txt の最後に test line という行を足して記録し、GitHub に送って PR を作ってください。そして、合流させずに、PR を閉じて、GitHub と手元の枝を片付けてください。

ヒント

PR の「Conversation」タブの下のほうに、「Merge pull request」のほかに、「Close pull request」（PR を閉じる）ボタンがあります。手元では、先に git fetch --prune で名残を刈り取ってから、枝を消します。手元の枝は main に合流していないので、第6章の「-d と -D」を、思い出してください。

こたえと解説 
git switch main
git switch -c try-close
notepad hello.txt
git add hello.txt
git commit -m "Add test line"
git push -u origin try-close

GitHub で PR を作ったら、「Close pull request」を押します。印が、赤の「Closed」になります（紫の「Merged」とは違います）。出てきた「Delete branch」で、GitHub の枝を消します。

手元では、main に戻り、先に名残を刈り取ってから、枝を消そうとします。

git switch main
git fetch --prune
git branch -d try-close
PS C:\work\my-notes> git branch -d try-close
error: the branch 'try-close' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D try-close'

not fully merged（合流していない）と、止められました。（hint: の行は、Git の版によって、少し違うことがあります。）今回は「要らない」と分かっていて、捨てるので、ここは大文字の -D で消します。

git branch -D try-close
順番に注意：fetch --prune が先 push -u で送り先を覚えさせた枝では、-d は「送り先（origin/try-close）に、送ってあるか」を先に確かめます。名残（origin/try-close）が手元に残っている間は、「送ってあるから大丈夫」と判断して、警告を出しながらも、消してしまいます。名残を刈り取ってからなら、今いる main に合流しているかで判断するので、止めてくれます。

main の hello.txt には、test line は入っていません。PR は「提案」なので、合流させなければ、main は変わりません。閉じた PR も、「Closed」の一覧に残ります。

🎯 チャレンジ3 ★★★　2つの PR を、同時に出す

次の2つの作業を、別々の枝・別々の PR にして、2つとも開いた状態にしてから、順に合流させてください。

  1. 枝 add-todo：todo.txt を作り、buy milk と書く
  2. 枝 add-links：links.txt を作り、https://github.com と書く

最後に、手元の main に、両方のファイルが届いていることを確かめてください。

ヒント

2つ目の枝を作る前に、git switch main で、main に戻ってから作ります。add-todo にいるまま作ると、add-links に todo.txt も入ってしまいます。

こたえと解説 
git switch main
git switch -c add-todo
New-Item todo.txt
notepad todo.txt
git add todo.txt
git commit -m "Add todo.txt"
git push -u origin add-todo

git switch main
git switch -c add-links
New-Item links.txt
notepad links.txt
git add links.txt
git commit -m "Add links.txt"
git push -u origin add-links

GitHub で、2つの PR を作ります。「Pull requests」タブに、2つが並んで開いているはずです。それぞれの「Files changed」には、自分の枝のファイルだけが出ています。1つずつ「Merge pull request」→「Confirm merge」→「Delete branch」と進めます。1つ目を合流させたあとでも、2つ目は「This branch has no conflicts with the base branch」（合流先の枝と、ぶつかるところはありません）と出て、そのまま合流できます。別々のファイルを変えたからです。

git switch main
git pull
git branch -d add-todo
git branch -d add-links
git fetch --prune
ls

ls で、todo.txt と links.txt の両方が見えれば、成功です。作業ごとに枝と PR を分けておけば、片方だけを先に合流させたり、片方だけを取りやめたりできます。

2つの PR が、同じ行を変えていたら？ 1つ目を合流させたあと、2つ目の PR に「This branch has conflicts that must be resolved」（解決が必要な衝突があります）と出て、そのままでは合流できません。これが、第6章で触れた「コンフリクト（衝突）」です。次の第8章で、わざと起こして、解消します。

確認クイズ

Q1. Pull Request（PR）とは、ひとことで言うと、何ですか？

「この枝を、main（などの枝）に合流させてください」という提案。GitHub の画面で作り、変更の一覧を見直してから、合流させる。

Q2. 枝 add-profile を、初めて GitHub に送るコマンドは？

git push -u origin add-profile。-u で送り先を覚えさせるので、この枝では、次から git push だけで送れる。

Q3. PR を作ったあとで、直したいところが見つかりました。PR を作り直す必要がありますか？

ない。手元の同じ枝で直して、commit → git push すれば、PR は自動で更新される。

Q4. GitHub で PR を合流させました。手元の main にも、すぐに変更が入っていますか？

入っていない。合流したのは GitHub の main だけ。git switch main → git pull で、手元に受け取る。

Q5. GitHub で「Delete branch」を押したのに、git branch -a に remotes/origin/add-profile が残っています。どうすれば消えますか？

git fetch --prune。GitHub で消えた枝の、手元に残った古い情報を、刈り取る。
